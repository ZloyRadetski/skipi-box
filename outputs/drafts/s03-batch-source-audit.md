# S03 batch refresh source audit

Read-only audit at `3d87f1c` (`refactor/desktop-shared-outbound-plan`), 2026-10-23. Scope: common batch refresh operation and Android/Desktop Home bindings, progress, eligibility, failure and cancellation behavior. Production and test sources were not changed; no tests or builds were run.

## Contract and current path

The pre-migration Android `updateAllSubscriptions()` captured `stateStore.state.value.subscriptionGroups.updatableSubscriptionGroups()`, marked those IDs refreshing, called `updateSubscriptions()`, applied successful responses, reported mixed results, and cleared progress in `finally`. `updateSubscriptionsFromResponses()` wrapped concurrent per-group loads in `withContext(Dispatchers.Default)`; each load used the shared per-group mutex. `updatableSubscriptionGroups()` now delegates to the common predicate: enabled and nonblank URL, preserving catalog order.

The current common `SubscriptionRefreshBatchOperation` captures the host catalog inside its re-entry mutex, filters eligibility, exposes all eligible IDs until load and commit finish, and clears them in `finally`. `refreshSubscriptions()` keeps per-request failures isolated while propagating cancellation. One successful load follows the existing single-commit path; two or more successful loads follow the aggregate catalog then metadata/profile path. Android captures from the live app-state store; Desktop captures the current shared subscription catalog and commits through its live repositories. The Home surfaces collect the runner’s progress and combine it with per-subscription progress. Mixed fetch outcomes are formatted using updated and failed counts; no eligible requests produce the existing no-updates message.

The aggregate cancellation boundary is covered in common and Android parity tests: cancellation after Android’s catalog write still reaches the metadata/profile write, while the operation still reports cancellation. Desktop also tests cancellation after its durable server-library write and notification of captured commit flags.

## Remaining issue

**P2 — Android import parsing now resumes on the Home UI dispatcher.** The old Android bulk loader explicitly ran all request work under `Dispatchers.Default` (`git show e4c438d^:app/src/main/kotlin/features/subscription/usecase/SubscriptionUpdateUseCase.kt`, lines 60–90). Today `ProxyHomeStore` launches the Home effect using `rememberCoroutineScope()` in `ProxyServerListPage`; `SubscriptionRefreshBatchOperation` and `refreshSubscriptions()` inherit that dispatcher (`shared/app/.../SubscriptionRefreshBatch.kt`, lines 203–229; `shared/app/.../SubscriptionRefreshUseCase.kt`, lines 47–62). `AndroidSubscriptionFetcher.fetchResponse()` switches only the network/decryption block to `Dispatchers.IO` and then returns to its caller; `loadSubscriptionRefresh()` immediately parses/imports the response, and Android’s Mihomo YAML loader calls SnakeYAML synchronously (`app/src/main/.../AndroidSubscriptionFetcher.kt`, lines 50–70; `shared/app/.../SubscriptionRefreshOperation.kt`, lines 98–110; `app/src/main/.../ProxyServerMihomoYamlImport.kt`, lines 17–26; `shared/yaml-jvm/.../MihomoYamlLoader.kt`, lines 14–15). Large subscription responses can therefore block the UI during import. Restore a background dispatcher for Android loading/import (at the host boundary or an appropriate common execution boundary) while leaving commit/UI callbacks on their existing dispatcher.

## Existing tests and verification gaps

Common coverage includes aggregate order/reference/selection/profile reconciliation, stale/deleted identity filtering, mixed fetch success/failure, eligibility, single-versus-batch commit selection, write failures, re-entry/progress, and cancellation cleanup (`SubscriptionRefreshBatchTest`, `SubscriptionRefreshBatchCancellationTest`). Android coverage includes live-state aggregate apply, enabled/nonblank eligibility, actual retained runner progress/re-entry and per-ID lock option timing, plus the post-catalog-write cancellation parity test. Desktop coverage includes actual repository batch commits, progress, commit-change callback behavior, partial profile-save failure, and cancellation after durable server write; Home effect/capability tests confirm the callback is exposed and invoked.

I found no test asserting that Android batch parsing stays off the main dispatcher, and no focused test joining Android Home’s `RefreshAllSubscriptions` effect to the retained runner and its error/progress behavior. The source path is connected, but these remain verification gaps for the end-to-end UI binding.
