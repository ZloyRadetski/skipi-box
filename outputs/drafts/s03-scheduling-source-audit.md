## Source contracts and call paths

### Android subscription periodic refresh

The shared interval parser in [`SubscriptionSchedule.kt`](../../shared/core/src/commonMain/kotlin/features/subscription/SubscriptionSchedule.kt#L18) treats blank and non-positive values as disabled; positive values below 0.25 hours, malformed values, and millisecond overflow as invalid. It accepts 0.25 hours as the WorkManager minimum. [`SubscriptionRefreshScheduling.kt`](../../shared/core/src/commonMain/kotlin/features/subscription/runtime/SubscriptionRefreshScheduling.kt#L90) builds one persistent spec per enabled group with a nonblank URL and enabled interval, uses unique name `subscription-update-<id>`, requires a connected network, sets `UPDATE`, uses a 15-minute backoff base, cancels formerly tracked IDs that are no longer eligible, then stores the desired ID set.

The live Android path is:

1. [`SkipiApplication.initializeRuntime`](../../app/src/main/kotlin/app/SkipiApplication.kt#L85) observes the persisted group list; its key tracks ID, URL, interval and enabled state, then calls the Android adapter `SubscriptionScheduler.reconcile`.
2. [`SubscriptionScheduler.kt`](../../app/src/main/kotlin/features/subscription/runtime/SubscriptionScheduler.kt#L8) maps `SubscriptionGroupState` to the shared target. [`AndroidSubscriptionScheduleGateway.kt`](../../app/src/main/kotlin/features/subscription/runtime/AndroidSubscriptionScheduleGateway.kt#L27) builds a `PeriodicWorkRequest` with group ID input, `NetworkType.CONNECTED`, exponential backoff, tag `subscription-update`, and `ExistingPeriodicWorkPolicy.UPDATE`; it persists scheduled IDs in private preferences and cancels by unique name.
3. [`SubscriptionWorker.doWork`](../../app/src/main/kotlin/features/subscription/runtime/SubscriptionWorker.kt#L19) returns success for a missing ID, failure if its application context is not `SkipiApplication`, otherwise delegates to `SubscriptionWorkerRunner` and maps its result to WorkManager success/retry/failure.
4. [`SubscriptionWorkerRunner`](../../app/src/main/kotlin/features/subscription/runtime/SubscriptionWorkerRunner.kt#L19) re-reads current app state and skips removed, disabled, or blank-URL groups with success. For an eligible group it updates one group; the fetch options use that group's proxy/Age fields plus current device-header and timeout settings (`SubscriptionUpdateUseCase.kt:270-276`).
5. The original Android worker runner at `77e4973^` performed the same eligibility and outcome mapping inline. Current shared [`SubscriptionWorkerPolicy.kt`](../../shared/app/src/commonMain/kotlin/app/skipi/app/subscription/SubscriptionWorkerPolicy.kt#L13) extracts only “skip missing/disabled/blank URL” and “empty failures = success, any transient failure = retry, otherwise permanent failure.” Android still classifies transient exceptions in [`SubscriptionFailureClassifier.kt`](../../app/src/main/kotlin/features/subscription/SubscriptionFailureClassifier.kt#L27): HTTP 408, 429, 5xx and listed connection/socket/DNS errors are transient. The Android worker maps `updateViaProxy && proxyRunning`, Age key, device-header setting and fetch timeout into each request.

### Android expiry reminders and background triggers

Portable reminder units, serialization, validation, defaults, and earliest-future-trigger selection are in [`SubscriptionExpiryReminder.kt`](../../shared/core/src/commonMain/kotlin/features/subscription/SubscriptionExpiryReminder.kt#L8) and [`SubscriptionExpirySchedule.kt`](../../shared/core/src/commonMain/kotlin/features/subscription/SubscriptionExpirySchedule.kt#L6). A target is eligible only when the global setting and group enabled/notify flags are true, expiry is positive, and an effective reminder has a trigger strictly after `now`. `customReminders == null` uses the global list; an empty custom list suppresses reminders.

The Android background path is:

1. `SkipiApplication.initializeRuntime` observes expiry enabled/global-reminder/group expiry inputs at [`SkipiApplication.kt`](../../app/src/main/kotlin/app/SkipiApplication.kt#L179), immediately checks and sends any now-due reminders, then schedules the next alarm.
2. [`SubscriptionExpiryScheduler`](../../app/src/main/kotlin/features/subscription/notification/SubscriptionExpiryScheduler.kt#L18) uses one explicit broadcast `PendingIntent` and the earliest shared trigger, scheduled as `RTC_WAKEUP` via `setAndAllowWhileIdle` on M+ (plain `set` before M). Turning the global setting off cancels that alarm. A no-future-trigger result returns without canceling an already pending alarm; when that alarm fires, the receiver re-reads state and recalculates.
3. The manifest registers [`SubscriptionExpiryReceiver`](../../app/src/main/AndroidManifest.xml#L245). It uses `goAsync`, loads the persisted app state, calls the Android notifier and re-schedules from that state (`SubscriptionExpiryReceiver.kt:15-29`). The notifier filters enabled/opted-in groups, uses custom reminders or global defaults, stores per-group/per-expiration sent reminder strings in preferences, and posts localized Android notifications (`SubscriptionExpiryNotifier.kt:42-126`).
4. The registered [`BootReceiver`](../../app/src/main/AndroidManifest.xml#L337) handles boot/package replacement for **auto-connect only**; it contains no direct expiry-alarm call. However, starting that receiver process also runs `SkipiApplication.onCreate`, which starts `initializeRuntime` and its expiry-state observer. So the current source has an indirect app-start rearm path on boot, with no test proving the full boot-to-alarm chain. Preserve the existing trigger path unless S03’s source review authorizes a separate behavior change.

Desktop persists the global expiry preference fields through [`DesktopApplicationRepositories.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopApplicationRepositories.kt#L502), and common UI models include the reminder values. Its settings screen currently sets `expiryNotifications = false` at [`DesktopSettingsScreen.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopSettingsScreen.kt#L636), so that UI hides the option. No Desktop caller of `SubscriptionExpirySchedule`, native notification publisher, or expiry timer was found. This audit does not infer or add a Desktop notification capability.

### Current Desktop subscription periodic host

Desktop has a separate, app-composition scheduler for subscription groups in [`Main.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/Main.kt#L197). It plans from `subscriptionLibrary` and wall-clock time, selects the first due subscription, stores its ID, then waits/clamps to a 1-second minimum and 1-hour idle delay. [`DesktopSubscriptionRefreshPlanner`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopSubscriptionRefreshPlanner.kt#L31) adapts stored subscriptions into the common planner; the common plan considers `lastUpdatedAtMillis + interval`, with a never-refreshed timestamp immediately due (`SubscriptionRefreshScheduling.kt:120-127`). The Planner tests cover elapsed/never-updated, eligibility, invalid interval and earliest future wakeup.

There is a concrete screen-lifetime coupling. The only due-ID consumer is [`DesktopProxyHome`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopProxyHome.kt#L189), which invokes `onUpdateSubscriptionById` and then clears the ID. [`Main.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/Main.kt#L1080) composes that screen only for `SkipiMainDestination.Proxy`. While another destination is open, the app-level scheduler can set `scheduledSubscriptionId`, but no composable consumes it; the scheduling effect then returns while that ID is non-null (`Main.kt:204-205`). A due subscription remains pending until the Proxy destination is composed again. Android WorkManager execution has no screen consumer.

The Desktop callback reaches the existing single-refresh path and same persisted libraries, but on network/load failure it only shows an error and clears `subscriptionUpdateInProgress` (`Main.kt:1702-1708`). There is no schedule result/backoff state update. Since the timestamp-based planner still sees the unchanged `lastUpdatedAtMillis` as due, the app-level effect can try again after its 1-second minimum. This differs from the Android worker's `Result.retry()` plus the configured exponential 15-minute base, and can create a tight repeated request loop after failure. The fetch options also use current Desktop runtime/settings from the existing callback (`Main.kt:1639-1643`).

The P03 profile and geo-resource periodic hosts at `Main.kt:589-644` use `runDesktopAutomaticRefreshLoop`; they refresh traffic-config documents or geo resource files, not `DesktopSubscriptionLibrary`. Their existence does not remove the subscription route coupling or supply subscription worker outcomes. No exact `runGeoResourcePeriodicRefreshHost` or `runTrafficConfigPeriodicRefreshHost` symbol exists at this HEAD; the reusable generic timer loop is `runDesktopAutomaticRefreshLoop`.

## Existing source-level proof and unproven edges

Current source contains these relevant tests (this audit inspected files and did not execute them):

- Shared core: `SubscriptionScheduleTest` exercises disabled/invalid/valid intervals and numeric boundaries. `SubscriptionRefreshSchedulingTest` exercises due/earliest timing, ineligible targets, stale-ID cancellation, and the generated shared work spec. `SubscriptionExpiryScheduleTest` exercises earliest eligible reminder, global disable, already-due trigger, and nonpositive expiry. `SubscriptionExpiryReminderTest` covers unit conversion, serialized compatibility and validation.
- Shared app: `SubscriptionWorkerPolicyTest` covers skip eligibility and empty/permanent/transient/mixed failure outcome mapping.
- Android: `SubscriptionWorkerRunnerTest` covers missing/disabled/blank group skip, transient retry, permanent failure and successful update. `SubscriptionExpirySchedulerTest` checks that one eligible fixture schedules the expected earliest `RTC_WAKEUP` alarm. `SubscriptionExpiryReminderTest` covers Android model defaults, units, serialization and list sorting.
- Desktop: `DesktopSubscriptionRefreshPlannerTest` covers plan timing and eligibility only. No test references the main subscription due-ID handoff or runs the periodic subscription path through a non-Proxy destination.

Current source-test gaps relevant to completing S03:

- No `AndroidSubscriptionScheduleGateway`/WorkManager test verifies request class/input, connected constraint, UPDATE, exponential delay, cancellation and tracked-ID persistence together.
- No test exercises `SubscriptionWorker.doWork` input/context guards and the final `Result.success/retry/failure` mapping through the Android worker adapter; runner tests stop at the internal enum/policy result.
- No Desktop host test proves a due request runs when Proxy UI is not composed. Existing Desktop planner tests cannot prove an actual refresh is dispatched.
- No Desktop schedule outcome/backoff/offline-admission test pins the current mismatch with Android. Root should decide the exact source-derived contract before changing timer policy; do not introduce an arbitrary retry delay or connectivity rule.
- Expiry schedule policy has shared unit coverage, but Android AlarmManager coverage is a single positive scheduling case; no current tests cover disable/cancel, no-next-trigger behavior, receiver reread/reschedule, notifier deduplication, or alarm restoration after reboot.
- No Desktop expiry timer or notification host exists, and the setting is hidden there. Confirm whether S03 expects any Desktop expiry runtime beyond Android’s current source-supported host before adding capability.

## Smallest proposed tests-first slice

Start with one Desktop subscription-host seam that owns the already-existing planner plus due-ID dispatch at the app lifetime. First add a behavior test using a due stored subscription while the Proxy screen is absent (for example, a Settings destination): the host must dispatch that subscription once and clear/replan after the existing refresh callback completes. Then wire the existing `onUpdateSubscriptionById` operation into that host rather than making `DesktopProxyHome` the only consumer. Keep the shared eligibility parser and existing refresh/commit operation; do not duplicate the P03 profile executor or invent a retry/conflict policy. Preserve a separate follow-up test gate for retry outcomes, because the observed 1-second repeat after failure does not match Android’s current classified WorkManager retry path and needs its exact policy derived from the Android contract before implementation.

The repository-level tests-first instruction in `AGENTS.md` applies before any production change: commit/add the new behavioral test, capture the expected RED (or baseline if the current host seam is not independently observable), then implement the minimum app-lifetime dispatch wiring and report GREEN.
