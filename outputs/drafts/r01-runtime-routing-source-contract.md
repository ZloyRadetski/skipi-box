# R01 — Runtime routing and persisted-data parity notes

Read-only follow-up, 23 October 2026. This traces existing runtime and backup paths so the next R01 slice can be scoped without adding a routing screen or choosing new precedence rules.

## Android source and profile precedence

- **Global AppState defaults are empty/Proxy/AsIs.** `DefaultRouteRules` is `emptyList()`, `routeDomainStrategy` defaults to `0`, `defaultRouteOutboundTag` to `proxy`, and `nextRouteRuleId` to `10` ([defaults](../../app/src/main/kotlin/app/AppStateDefaults.kt:32), [strategy](../../app/src/main/kotlin/app/AppState.kt:154), [outbound and IDs](../../app/src/main/kotlin/app/AppState.kt:155)).
- **The generated Xray compiler consumes the fields of the AppState it receives.** `AppState.buildXrayRoutingPlan` forwards `routeDomainStrategy`, `routeRules`, and `defaultRouteOutboundTag` to the shared `XrayRoutingRequest` ([Android adapter](../../app/src/main/kotlin/engine/xray/XrayRoutingConfig.kt:10)); `XrayConfigFactory` uses that plan for generated configs ([builder](../../app/src/main/kotlin/engine/xray/XrayConfig.kt:194)). `nextRouteRuleId` is not an Xray planner input; it is allocation state for later rule edits.
- **A normal Android VPN start first projects the selected profile onto AppState.** `AndroidProxyEngine.startUnlocked` resolves network settings, calls `withActiveTrafficConfigApplied()`, then applies strict-tunnel policy before handing that state to the Xray builder ([start path](../../app/src/main/kotlin/engine/proxy/AndroidProxyEngine.kt:127)); the Always-on VPN path applies the active profile too ([Always-on path](../../app/src/main/kotlin/engine/vpn/SkipiVpnService.kt:213)). `withActiveTrafficConfigApplied` replaces the three global routing fields with the profile plan and its profile domain strategy ([projection](../../app/src/main/kotlin/app/TrafficConfigRuntime.kt:14)). When strict full-tunnel mode is enabled, the later copy changes any final Direct default to Proxy and disables enabled Direct-target rules without changing stored settings ([strict mode](../../app/src/main/kotlin/engine/vpn/StrictFullTunnel.kt:20)).
- **That runtime profile plan originates in Shadowrocket `[Rule]` and `[SKIPI]`.** It converts non-`FINAL` rules to route rules and resolves the final policy as the default outbound ([planner](../../shared/core/src/commonMain/kotlin/features/config/TrafficConfigRuntimePlan.kt:79)). Domain strategy is read from the profile’s `route-domain-strategy` key with that profile’s Android settings as fallback ([profile decode](../../shared/core/src/commonMain/kotlin/features/config/TrafficConfigDocument.kt:129)); `withActiveTrafficConfigApplied` then copies it to runtime AppState. The built-in profile contains `FINAL,PROXY` and no non-final rules ([default document](../../shared/core/src/commonMain/kotlin/features/config/ShadowrocketConfig.kt:477)), so its projected routing is empty rules, Proxy default, and the profile’s AsIs default. This happens to match the global AppState defaults.
- **Implication for persisted legacy global rules:** a nonempty global AppState route list/default can be persisted and passed to the compiler, but a normal VPN start with an active traffic profile projects the profile’s rules/default over those values first. Do not assume that “use DesktopAppSettings routing in runtime” is equivalent to mirroring Android’s active-profile path; profile rules and global routing are distinct sources, and precedence needs an explicit product/source decision.

## Desktop generated configuration and concrete gap

- `buildDesktopSelectedServerConfig` routes a selected custom Xray server through its custom adapter; otherwise it uses the selected traffic profile when one exists, and falls back to the selected-server factory when no profile is selected ([branching](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopSelectedServerConfig.kt:24)). The Desktop profile branch builds from profile content, uses Shadowrocket rules, and reads profile `route-domain-strategy` ([profile factory](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopTrafficProfileXrayConfig.kt:55)). This is profile routing, not global settings.
- **The no-profile selected-server path ignores persisted global routing fields.** Desktop’s settings model stores `routeRules`, `defaultRouteOutboundTag`, `routeDomainStrategy`, and `nextRouteRuleId` ([settings fields](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopSettingsLibrary.kt:104)), but neither the selected-config entrypoint nor `DesktopSelectedServerXrayConfigFactory.build` accepts those settings. That factory passes `routeRules = emptyList()` and `defaultRouteOutboundTag = XrayTags.PROXY` ([factory inputs](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopSelectedServerXrayConfigFactory.kt:20)). Since the shared outbound planner only adds additional server targets referenced by enabled rules or the default tag ([target selection](../../shared/app/src/commonMain/kotlin/app/skipi/app/proxy/XrayOutboundPlanner.kt:57)), rules/defaults targeting another server are omitted along with their dispatch rules. `LocalProxyXrayConfigFactory` also uses its own local routing strategy/defaults if it has to generate routing ([local planner](../../shared/core/src/commonMain/kotlin/platform/LocalProxyXrayConfig.kt:163)). A fresh Desktop config library is empty with `selectedConfigId = null` ([library defaults](../../shared/core/src/commonMain/kotlin/features/config/ConfigProfileLibrary.kt:20), [load behavior](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopConfigLibrary.kt:36)), so the no-profile branch is the ordinary fresh setup; a saved nonempty global rules/default/strategy value will not affect its generated selected-server config today.
- **The routing counter has no runtime parity effect by itself.** It is absent from `RoutingConfigRecord`/`XrayRoutingRequest` and only matters to future ID allocation. Android backups store route rules as a separate list plus route strategy/default in settings ([backup model](../../shared/core/src/commonMain/kotlin/features/backup/AppBackupModels.kt:135)); restore reconstructs the counter as `max(default 10, max restored rule ID + 1)` rather than importing a counter ([restore](../../app/src/main/kotlin/data/backup/AppBackupMapper.kt:363), [allocator](../../app/src/main/kotlin/data/backup/AppBackupMapper.kt:502)). Desktop persists the counter in settings, and the routing repository keeps its high-water value during updates; the current Xray factory does not read it. Keep counter preservation in the repository/editor contract, separate from runtime config generation.

## Scope conclusion

There is a concrete, bounded parity gap for already-saved Desktop global routing data in the **no-active-profile generated selected-server path**: nonempty persisted rules and a changed default outbound/domain strategy are ignored in favor of fixed local defaults. The profile-selected path already consumes profile Shadowrocket routing and should remain separate. Android’s live VPN path also applies the profile before compiling Xray, so any claim that these global fields must override an active profile needs a separate precedence decision. The high-water ID counter is important for safe future edits, not Xray output. No production files, tests, builds, or Git state were changed for this audit.
