# R03 Android app inventory and VPN policy audit

Status: read-only source audit before R03 tests or production changes. Source checkpoint supplied for this audit: `77f217c` on `refactor/desktop-shared-outbound-plan`. No tests, builds, device operations, package enumeration, or source edits were performed. This draft is the only file written for this audit.

## Findings

The Per-App editor is profile-scoped. Android's `ProxyAppListPage` requires a `trafficConfigId`, loads that exact profile, and sends immediate mode, selection, and import updates through the shared P04 editor/controller. The common screen already owns the portable profile editing, clipboard, and selection actions. R03 should not add a second global Per-App editor or repeat P04's screen/controller work. [ProxyAppListPage.kt](../../app/src/main/kotlin/features/proxy/app/ProxyAppListPage.kt#L70), [P04 source specification](../shared-migration-20261023/p04-per-app-screen-source-spec.md#L1)

At VPN start, the active profile is the source of the effective per-app mode and selected IDs: `withActiveTrafficConfigApplied()` copies `TrafficConfigState.proxyAppListMode` and `.proxyAppListSelectedApps` onto the effective `AppState`. `activeTrafficConfig()` resolves the configured active ID, falling back to the first profile if that ID is missing; the AppState fields remain effective only when there is no profile. Normal Android starts apply this profile before strict-full-tunnel processing, and the system-managed Always-on start applies it before creating the service config. Strict-full-tunnel then forces global mode and clears only the runtime selection, leaving the stored profile unchanged. [TrafficConfigRuntime.kt](../../app/src/main/kotlin/app/TrafficConfigRuntime.kt#L13), [AndroidProxyEngine.kt](../../app/src/main/kotlin/engine/proxy/AndroidProxyEngine.kt#L128), [SkipiVpnService.kt](../../app/src/main/kotlin/engine/vpn/SkipiVpnService.kt#L208), [StrictFullTunnel.kt](../../app/src/main/kotlin/engine/vpn/StrictFullTunnel.kt#L11)

The repository has both profile fields (`TrafficConfigState`) and older/global AppState fields with the same meaning. The profile fields are written to `[SKIPI] per-app-mode` / repeated `per-app-package` document values and are mapped through profile backup. The AppState fields are also represented in app settings and the top-level backup `proxyAppListSelectedApps`. I found no global Per-App settings editor path; treat the profile-scoped page and active-profile override as the runtime contract, and retain the AppState fields as a separate compatibility/fallback source until history proves more. [TrafficConfigDocument.kt](../../shared/core/src/commonMain/kotlin/features/config/TrafficConfigDocument.kt#L39), [AppState.kt](../../app/src/main/kotlin/app/AppState.kt#L205), [AppBackupModels.kt](../../shared/core/src/commonMain/kotlin/features/backup/AppBackupModels.kt#L134), [AppBackupTrafficConfig mapper](../../shared/core/src/commonMain/kotlin/features/backup/AppBackupMappers.kt#L81)

The remaining pure Android-only logic falls into two seams that can be characterized and moved without creating Desktop inventory or enforcement:

- `ProxyAppListData.kt` converts host-supplied package records into sorted list rows, groups by user and shared UID, creates user-space tabs, counts checked rows, filters by trimmed case-insensitive name/package search, and prioritizes selected rows during refresh. These decisions do not require `PackageManager`; the host inventory record can remain an input. Preserve the current key shape `${userId}:$packageName`, shared-UID multi-key toggle, unknown stored IDs, fixed-user remapping/deduplication, and sort order. [ProxyAppListData.kt](../../app/src/main/kotlin/features/proxy/app/model/ProxyAppListData.kt#L101)
- `AppState.toVpnApplicationPolicy()` and `toVpnServicePackageNames()` normalize the effective mode and selected IDs before handing them to the service. The pure rules are: strict mode or an unknown mode resolves to global; global ignores selections; a qualified ID is kept only when its user prefix matches the process user; legacy IDs without a colon pass through; remaining names are trimmed, empty values removed, and duplicates removed in encounter order. This projection can be factored behind a common value API, while `Process.myUid()`, strict-setting composition, own-package identity, installed-package checks, and `VpnService.Builder` calls remain Android host work. [VpnApplicationPolicy.kt](../../app/src/main/kotlin/engine/vpn/VpnApplicationPolicy.kt#L12)

Package inventory, app labels/icons, system classification, user-profile discovery, self-package identity, PackageManager compatibility calls, and VPN enforcement are actual Android adapters. Do not replace them with Desktop package discovery or runtime policy. The package repository calls `getInstalledApplications(0)` for the PackageManager's current user, maps system status from `FLAG_SYSTEM` or `FLAG_UPDATED_SYSTEM_APP`, and does not issue a per-`UserHandle` package query. Package-record user IDs come from `uid / 100000`; app IDs come from `uid % 100000` when the fixed-user projection remaps an entry. `AndroidUserSpaceRepository` separately lists `UserManager.userProfiles`, converts each handle with `hashCode()`, and falls back to the current process user on failure. The inventory and user-space adapters should be tested as they exist before considering any change to profile coverage or identity mapping. [AndroidPackageRepository.kt](../../app/src/main/kotlin/system/AndroidPackageRepository.kt#L18), [ProxyAppListData.kt](../../app/src/main/kotlin/features/proxy/app/model/ProxyAppListData.kt#L156), [AndroidConstants.kt](../../app/src/main/kotlin/system/AndroidConstants.kt#L6), [AndroidUserSpaceRepository.kt](../../app/src/main/kotlin/system/user/AndroidUserSpaceRepository.kt#L21), [AndroidPackageCompat.kt](../../app/src/main/kotlin/system/AndroidPackageCompat.kt#L10)

## Source-derived VPN policy baseline

`VpnXrayConfigFactory` derives the service policy using `Process.myUid().toAndroidUserId()`. The service constructs a fresh `VpnService.Builder` for each tunnel and uses exactly one application-list method family for that start:

| Effective mode | Android Builder calls | Baseline consequence |
| --- | --- | --- |
| Global or unknown mode | `addDisallowedApplication(selfPackageName)` | All apps are eligible for the VPN except Skipi itself. Stored selections do not affect global mode. |
| Blacklist | `addDisallowedApplication(selected + selfPackageName)` | Trim, drop blank names, and dedupe before adding. Skipi remains bypassed even if omitted from stored IDs. |
| Whitelist with one or more accepted app names | `addAllowedApplication(selected minus selfPackageName)` | Only accepted entries may use the VPN. Skipi is filtered out of the allow list. |
| Whitelist with zero accepted names | `addDisallowedApplication(installedPackageNames())` | Avoids Android's default-all behavior when no allow call occurs; deny every name returned by the current-user installed-app query. |

The policy is normalized before the builder: colon-prefixed IDs for other users are removed; the current-user prefix is stripped to produce a package name; unqualified legacy IDs are passed through. For each add call the service catches `PackageManager.NameNotFoundException` and silently skips that name. Other exceptions propagate and fail tunnel startup. Consequently, a stale or unknown profile ID is preserved in storage/backup but is not added to the runtime builder. If every whitelist selection is stale, foreign-user, blank, or Skipi itself, the empty-list deny-all fallback applies. [VpnApplicationPolicy.kt](../../app/src/main/kotlin/engine/vpn/VpnApplicationPolicy.kt#L17), [VpnXrayConfig.kt](../../app/src/main/kotlin/engine/vpn/VpnXrayConfig.kt#L155), [SkipiVpnService.kt](../../app/src/main/kotlin/engine/vpn/SkipiVpnService.kt#L379)

The app-list inventory uses `showSystemApps = true` to request scope `all` and false to request scope `user`; the repository's system filter only checks `FLAG_SYSTEM` and `FLAG_UPDATED_SYSTEM_APP`. The row model has a `system` bit but no Android package-enabled state. The row's UI `enabled` flag means “the mode is not Global,” so it disables app selection for Global mode, not because the installed Android application is disabled. `getInstalledApplicationsCompat()` passes flags `0` on both API branches, and production code does not read `ApplicationInfo.enabled`. Therefore tests should characterize the PackageManager result for disabled apps rather than invent an app-enabled rule in shared code. No `MATCH_UNINSTALLED_PACKAGES` flag is used. [ProxyAppListData.kt](../../app/src/main/kotlin/features/proxy/app/model/ProxyAppListData.kt#L60), [ProxyAppListPage.kt](../../app/src/main/kotlin/features/proxy/app/ProxyAppListPage.kt#L329), [AndroidPackageRepository.kt](../../app/src/main/kotlin/system/AndroidPackageRepository.kt#L53), [AndroidPackageCompat.kt](../../app/src/main/kotlin/system/AndroidPackageCompat.kt#L18)

These API constraints are documented by Android: `VpnService.Builder` allows either allowed apps or disallowed apps, requires a currently installed canonical package name, and throws `NameNotFoundException` for an uninstalled name; `getInstalledApplications` returns the current user's installed apps; `ApplicationInfo.enabled == false` means the app's components are disabled. [VpnService.Builder reference](https://developer.android.com/reference/android/net/VpnService.Builder#addAllowedApplication(java.lang.String)), [PackageManager reference](https://developer.android.com/reference/android/content/pm/PackageManager#getInstalledApplications(int)), [ApplicationInfo reference](https://developer.android.com/reference/android/content/pm/ApplicationInfo#enabled)

## Recommended tests-first order

1. **Capture the current projection oracle on Android first.** Exercise a fabricated `AppPackageEntry` inventory against `prepareProxyAppListData`, `sortedForProxyAppListRefresh`, and `toUserSpaceTabs`. Cases should pin trimmed/case-insensitive search across label and package name; current user key creation; fixed-user remap and package dedupe; fallback user tabs; shared UID rows selecting all keys; checked tab counts; selected-first refresh sorting; self-package exclusion; and preservation of unknown selected IDs in the profile while absent from the displayed inventory. This is the pure logic candidate for common code.
2. **Add the missing active-profile policy baseline.** Set distinct legacy AppState and profile per-app values and assert that the explicit active profile wins for VPN start, an invalid active ID uses the first profile, a non-active profile does not affect enforcement, and only an empty profile list leaves AppState values in effect. Assert strict-full-tunnel forces global and does not mutate the saved profile. Cover mode normalization plus current-user/other-user/legacy package-key conversion, whitespace, duplicates, and empty entries.
3. **Add an isolated PackageManager adapter characterization.** Under Robolectric, install synthetic packages into the sandbox PackageManager and exercise user/system scope, labels, UID-to-user/app decomposition, updated-system classification, excluded self package, and missing package-info label fallback. Include a disabled `ApplicationInfo` fixture to record what the existing `getInstalledApplications(0)` path returns and confirm that Skipi adds no separate enabled-state filter. Test the API compatibility branch at SDK 32 and 33 if useful; all data should be Robolectric fixtures, not host or phone inventory.
4. **Make the VPN policy-to-builder adapter observable and characterize calls.** Use a tiny internal call boundary or recorder for `addAllowedApplication`, `addDisallowedApplication`, and the installed-package fallback. Pin the mode table above; valid, stale, foreign-user, own-package, blank, duplicate, and non-`NameNotFoundException` outcomes; empty-whitelist fallback; and the invariant that one start never mixes allow and deny calls. A Robolectric service/builder smoke can stop after `add*Application` and before `establish()`, so it does not create a VPN interface or alter device routing. The current private extension has no observable call seam. A Builder smoke validates call admission/dispatch only; it does not prove kernel routing or traffic behavior.
5. **Strengthen profile backup coverage with a non-default profile row.** Round-trip a profile with whitelist/blacklist mode and unknown namespaced IDs through `TrafficConfigState -> AppBackupTrafficConfig -> TrafficConfigState` and the outer app backup mapper. Preserve the existing top-level AppState global fields independently. Do not couple profile storage to installed-app inventory.

Robolectric 4.16.1 and `androidx.test:core` are already `app` test dependencies. Robolectric's `ShadowPackageManager.installPackage(PackageInfo)` can provide package fixtures. `ShadowVpnService` documents `prepare`/`protect` behavior, but the current code does not expose the private builder operation list; a small recorder seam is the reliable policy-call assertion. Stop before `Builder.establish()` for this smoke. [app/build.gradle.kts](../../app/build.gradle.kts#L161), [Robolectric ShadowPackageManager](https://robolectric.org/javadoc/latest/org/robolectric/shadows/ShadowPackageManager.html), [Robolectric ShadowVpnService](https://robolectric.org/javadoc/4.12/org/robolectric/shadows/ShadowVpnService.html)

## Android-only adapter boundary

Keep these operations in Android code:

- `PackageManager` installed-app enumeration, label/icon lookup, actual `ApplicationInfo` flags, package availability checks, and Android API 33 flag compatibility.
- `UserManager.userProfiles`, `Process.myUid()`, `Process.myUserHandle()`, process-user ID calculation, and the app's package name from `Context`.
- Android `VpnService.Builder` calls, full-denylist inventory for the empty whitelist case, package installation checks, and VPN interface establishment.

Portable code may own the app-list projection and the mode/selection-to-request data mapping, but the Desktop host should continue storing/editing the shared profile mode and IDs without presenting fake Android apps or claiming per-app runtime enforcement.
