# S03 Desktop Main integration spec

Prepared read-only against `3d87f1c` on `refactor/desktop-shared-outbound-plan`, with the in-progress S03 shared/runtime contracts. This document specifies the remaining Main and Proxy Home wiring. No Main or Proxy Home source, tests, builds, or Git state were changed here.

## Current source path

`Main.kt` currently keeps a Compose-driven due-ID planner keyed by the local subscription library, UI busy flag, selected due ID, scheduler tick, and `closeRequested` ([Main.kt:167-225](../../desktopApp/src/main/kotlin/app/skipi/desktop/Main.kt#L167)). It stores the first due ID in `scheduledSubscriptionId`. `DesktopProxyHome` is its only consumer ([DesktopProxyHome.kt:189-196](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopProxyHome.kt#L189)), and Main renders that screen only when `currentSection == Proxy` ([Main.kt:1079-1082](../../desktopApp/src/main/kotlin/app/skipi/desktop/Main.kt#L1079)). A due subscription can therefore wait indefinitely while Configs or Settings is open.

The one-subscription operation is still inline in the `onUpdateSubscriptionById` callback ([Main.kt:1623-1709](../../desktopApp/src/main/kotlin/app/skipi/desktop/Main.kt#L1623)). It reads the current row and fetch options before launching, rejects a second caller via `subscriptionUpdateInProgress`, runs `refreshSubscription`, formats the UI result, and reconnects after visible server/profile changes. This UI callback cannot safely serve an app-lifetime worker because it belongs to Proxy Home and returns `Unit` before refresh completes.

Batch refresh is held by `DesktopSubscriptionRefreshBatchRunner` and captures the latest catalog/options from inside `run()` ([Main.kt:315-357](../../desktopApp/src/main/kotlin/app/skipi/desktop/Main.kt#L315)); its shared operation has its own re-entry guard. Both the current single and batch UI callbacks use the same boolean as an early rejection, rather than common serial admission ([Main.kt:1623-1647](../../desktopApp/src/main/kotlin/app/skipi/desktop/Main.kt#L1623), [Main.kt:1712-1723](../../desktopApp/src/main/kotlin/app/skipi/desktop/Main.kt#L1712)). Desktop install currently persists from a Proxy Home callback and separately starts the refresh callback; clipboard import reports “added” immediately without awaiting that refresh ([DesktopProxyHome.kt:461-472](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopProxyHome.kt#L461)).

## Approved contracts to wire

- The app-lifetime operation is `DesktopSubscriptionRefreshOperation.run(request: SubscriptionRefreshLoadRequest<DesktopSubscriptionRefreshFetchOptions>)`, returning `DesktopSubscriptionRefreshOperationResult(refresh: SubscriptionRefreshResult, serverLibraryChanged: Boolean, profileLibraryChanged: Boolean)`. It owns shared load/parse plus the real Desktop commit adapter, but not admission or request capture.
- Shared install orchestration is `installAndRefresh(repository, title, url, userAgent, refresh)`, returning `.preparation` (including the saved `existingTitle`) and `.refreshResult`. It persists before invoking the supplied callback once, and passes that callback the full saved record. Main must invoke it under the same host admission as other refresh work, then call the operation with options derived from that saved row. It must work for disabled duplicates because Android first-fetch behavior does not gate install on `enabled`.
- `DesktopSubscriptionAutoUpdater` accepts current `SubscriptionRefreshTarget`s, uses `isDesktopNetworkConnected`, invokes a suspend callback returning `SubscriptionWorkerOutcome`, and exposes `observeTargets`, `runDue`, and `nextWakeupAtMillis`. It uses the common `subscriptionRefreshWorkSpecOrNull` contract and subscription-specific periodic state; keep it separate from P03 profile/resource hosts.
- Scheduled eligibility must be re-read after admission with common `shouldFetchScheduledSubscription(groupFound, enabled, url)`. A now-missing, disabled, or blank-URL group returns `SUCCESS` without a fetch, matching Android. Manual refresh keeps the existing blank/missing checks and does not gain an enabled-only restriction. Install always runs the first fetch after persistence, even for a disabled saved record.
- Scheduled outcome matches the Android worker boundary: no load failure means `SUCCESS` unless commit reports a storage failure, which maps to permanent `FAILURE`; a thrown load/fetch/parse error maps through `isTransientDesktopSubscriptionRefreshFailure` to `RETRY` or `FAILURE`; cancellation propagates. A stale/non-applicable commit receipt with no commit failure is `SUCCESS`. Do not classify commit/storage exceptions as transient network failures.

## Smallest Main wiring

1. Remember one subscription admission `Mutex` with the Main-owned refresh services. Put request lookup and fetch-option capture *inside* admission so a queued manual or automatic request sees the latest `desktopSharedApplication.subscriptions.catalog`, settings, and Core state. A short private `runSavedSubscriptionRefresh(record)` can own request construction, `DesktopSubscriptionRefreshOperation.run`, existing result formatting, and reconnect handling; callers choose their own eligibility rule before calling it.
2. Route manual single refresh through a suspend host helper that acquires admission, re-reads the row by ID, preserves missing/blank messages, and then calls `runSavedSubscriptionRefresh`. Keep `refreshingSubscriptionId` and `subscriptionUpdateInProgress` as presentation state only. A queued request waits for admission or is explicitly reported as rejected; never turn “already busy” into an automatic worker `SUCCESS`.
3. Wrap `desktopSubscriptionRefreshBatchRunner.run()` in the same outer admission. Its own re-entry guard remains useful for duplicate batch invocations; the outer gate serializes its catalog capture/load/commit against single, install, and periodic operations. It is essential that the batch's `captureRequests` closure remains inside `run()` after admission rather than capturing rows before waiting.
4. Add a subscription-specific `DesktopSubscriptionAutoUpdater` and conflated wakeup `Channel` beside the existing app-lifetime P03 hosts ([Main.kt:523-568](../../desktopApp/src/main/kotlin/app/skipi/desktop/Main.kt#L523)). Observe targets from the shared subscription catalog when it changes, call `observeTargets`, then `trySend(Unit)`. Start `runDesktopAutomaticRefreshLoop` in a Main-level `LaunchedEffect` whose key includes `closeRequested`; if closure is requested, do not start the loop, and changing the key cancels its structured loop and due pass. Keep the existing connected-network check. The updater leaves disconnected work due and only calls its callback when connected, like WorkManager's connected constraint.
5. The updater callback acquires the same admission as manual/batch, then re-reads the row and calls `shouldFetchScheduledSubscription`. This is intentionally separate from `runSavedSubscriptionRefresh`: manual and installation do not use scheduled-worker eligibility. Convert load errors with the Desktop adapter/shared classifier and preserve commit-failure permanence. If waiting for admission delays a run past target disable/removal, the second eligibility check prevents a stale fetch.
6. Remove `scheduledSubscriptionId` and `subscriptionSchedulerTick` from Main and remove `scheduledSubscriptionId` / `onScheduledSubscriptionConsumed` plus the due-ID `LaunchedEffect` from `DesktopProxyHome`. Keep the existing Proxy Home manual refresh action and progress display.
7. Replace the install callback split with a suspend install-and-refresh callback. Under the shared admission, call `installAndRefresh` with the persisted Desktop repository and a callback that invokes `runSavedSubscriptionRefresh` on the saved row. Clipboard and manual Add handlers await that result before showing completion, use `.preparation.existingTitle` for duplicate wording through the shared saved-title formatter, and retain the refresh success/failure detail. Do not report an unconditional “added” result after only persistence.

## Behavioral QA before calling Main complete

The host tests for `DesktopSubscriptionAutoUpdater` establish app-host scheduling behavior independently of a screen; the existing P03 loop tests show how to verify deadlines, wakeups, structured cancellation, and background completion ([DesktopTrafficAutoUpdateLoopTest.kt](../../desktopApp/src/test/kotlin/app/skipi/desktop/DesktopTrafficAutoUpdateLoopTest.kt), [DesktopResourceAutoUpdateLoopTest.kt](../../desktopApp/src/test/kotlin/app/skipi/desktop/DesktopResourceAutoUpdateLoopTest.kt)). Main integration still needs behavior-level evidence for the actual connections:

- A shared admission/coordinator test should start a suspended single refresh, request a batch and due refresh, and assert no overlap, no dropped automatic `SUCCESS`, and latest catalog/options captured only after admission. It should disable or delete the due record while that request waits and assert that the post-admission check skips the fetch.
- An app-host test should observe a due target while the selected section is Configs or Settings, advance to the deadline, and assert the shared refresh operation ran without a Proxy Home consumer. This can test a small extracted Main host coordinator; a source grep alone does not prove the runtime route.
- Cancellation coverage should cancel the subscription loop owner through the same `closeRequested` lifecycle hook while fetch is suspended; assert cancellation reaches the operation and its late result cannot advance the removed/replaced schedule. Existing updater identity guards protect reconciled entries, but Main must exercise the real loop owner.
- Outcome tests should distinguish transient load exceptions (`RETRY` and exponential deadline), permanent load exceptions (`FAILURE` then next interval), commit/storage failure (`FAILURE` then next interval), stale/non-applicable commit (`SUCCESS`), and cancellation (propagated). Also assert a disconnected due target remains due until the connectivity predicate becomes true.
- Install integration should prove the saved row is persisted before the first refresh, a disabled duplicate still fetches using its saved fields, and the clipboard completion message awaits the refresh and names the saved duplicate title. Existing install API tests and the Desktop single-operation integration test can supply the persistence/commit evidence; the UI callback test should cover actual awaited message behavior.

The periodic state/host tests and in-progress single-operation/install tests do not by themselves prove these Main callback connections. Root owns Main edits, Gradle verification, and Git operations after the source/test gate.
