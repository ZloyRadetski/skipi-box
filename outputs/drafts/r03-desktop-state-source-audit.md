# R03 — Desktop and shared Per-App state source audit

Date: 24 October 2026
Scope: read-only source and accepted-P04 report review for R03. No production or test files were edited; no Gradle, build, Git, native, device, OS clipboard, or user-data operation was run.

## Finding

The portable profile editor is already connected to Android and Desktop by the accepted P04 work. Desktop has no global Per-App settings page or global Per-App route. Its Per-App entry is inside the selected traffic profile's visual editor. R03's remaining portable gap is the Android-owned installed-app projection and search/filter state: the selection mutator and clipboard codec are already common, while installed-package listing, row projection, search, shared-UID presentation, user-space tabs, and icons still live in the Android app module. Desktop can already change a profile's mode and selected IDs through the common editor and clipboard callbacks; it does not enumerate apps or apply the policy.

This matches the current R03 and P04 boundaries in [`tasks/plan.md`](../../tasks/plan.md#p04) and the accepted reports [`p04-acceptance-verification.md`](../../tasks/shared-migration-20261023/p04-acceptance-verification.md), [`p04-per-app-screen-verification.md`](../../tasks/shared-migration-20261023/p04-per-app-screen-verification.md), [`p04-per-app-controller-verification.md`](../../tasks/shared-migration-20261023/p04-per-app-controller-verification.md), and [`p04-per-app-foundation-verification.md`](../../tasks/shared-migration-20261023/p04-per-app-foundation-verification.md). The earlier research file's checklist/status commentary predates P04 acceptance; use its Android source contract as context, not its old P04 completion status.

## Actual route and platform ownership

Android's active Per-App route is profile-specific. [`TrafficConfigEditorPages.kt`](../../app/src/main/kotlin/features/config/TrafficConfigEditorPages.kt) pushes `Route.ProxyAppList(config.id)` from Basics; [`AppContent.kt`](../../app/src/main/kotlin/app/AppContent.kt) dispatches that route to `ProxyAppListPage`. The page resolves `trafficConfigId` in `AppState.trafficConfigs` and uses that row's `proxyAppListMode` and `proxyAppListSelectedApps`. It does not use the active profile as the edit target. The mode and selected ID writes go through the common `TrafficConfigEditorController` and `TrafficConfigEditorProfileStore`, so selecting profile 7 for editing while profile 3 remains active is an established case, not a Desktop-specific new behavior.

Android supplies `AndroidPackageProvider` and `AndroidUserSpaceProvider` through `LocalAppServices`. [`ProxyAppListData.kt`](../../app/src/main/kotlin/features/proxy/app/model/ProxyAppListData.kt) calls those providers, maps installed records to labels, package names, UIDs, and system-app flags, groups by Android user, makes shared-UID rows carry every selection key for that UID, and projects a trimmed case-insensitive search over label or package name. It also sorts selected/shared-UID rows during package refresh. [`AndroidAppIconFetcher.kt`](../../app/src/main/kotlin/system/AndroidAppIconFetcher.kt) obtains icons from Android's PackageManager. These are concrete Android adapters and should stay host-owned; the projection over the resulting plain records is portable.

The asynchronous page state is also Android-owned today: [`ProxyAppListPageState.kt`](../../app/src/main/kotlin/features/proxy/app/ProxyAppListPageState.kt) owns package refresh, search debounce, system-app toggle, selected Android user, and prepared rows. `ProxyAppListPage.kt` injects that host projection into the shared Per-App screen. The shared screen provides mode, clipboard, import confirmation, and immediate controller actions; the Android host supplies search, tabs, icons, and app rows.

## Desktop settings, profile storage, and policy boundary

[`DesktopSettingsScreen.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopSettingsScreen.kt) has no Per-App settings destination. [`DesktopAppSettings`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopSettingsLibrary.kt) has no app-list mode or selected-package fields, and the shared `PersistedSettings`/`ApplicationPreferences` contract has no such fields either. Desktop's Per-App entry appears in Basics of `DesktopConfigsScreen`; it passes the selected `TrafficConfigState` to the same `SkipiTrafficConfigProxyAppListEditorScreen` used on Android.

Desktop passes `currentUserId = null` and `selfPackageName = ""`, provides real clipboard callbacks, and shows a localized capability notice. The common clipboard decoder uses its existing `currentUserId ?: 0` fallback for bare package names. This is a serialization fallback only; it does not represent a discovered Desktop user. The Desktop body intentionally has no app rows, Android search, user tabs, system-app action, fake package identity, or package-name text editor. Accepted actual-screen tests cover More → UI Edit on an inactive profile, immediate mode change, Replace/Merge clipboard, missing/failed target, Back, no fake rows, and narrow/wide renders.

Desktop's traffic profile persistence is `configs.json`, not `settings.json`. `DesktopConfigLibraries` serializes the common `ConfigProfileLibrary` envelope; `ConfigProfile` stores `id`, `name`, `content`, URL/lock/timestamp metadata. The Per-App values are represented inside `content` as `[SKIPI] per-app-mode = blacklist|whitelist|global` and repeated `per-app-package` values. `DesktopTrafficConfigEditorProfileStore` reads the latest profile row by ID, transforms the common `TrafficConfigState`, then stores the new raw document. Existing file-backed tests verify immediate writes while preserving selected profile, order, next-ID counter, row metadata, siblings, and non-SKIPI document sections.

No Desktop runtime consumer applies these values. Desktop's current Xray/profile pipeline has no Android per-app package policy binding; the source comments in [`DesktopTrafficProfileXrayConfig.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopTrafficProfileXrayConfig.kt) explicitly classify per-app and VPN/TUN settings as Android-only. R03 should retain and edit the profile data on Desktop without adding application routing, a fake PackageManager, or a successful no-op that claims enforcement.

## Global settings versus profile state and precedence

Android still has legacy/global `AppState.proxyAppListMode` and `proxyAppListSelectedApps` fields. The former is stored in SharedPreferences (`proxy_app_list_mode`); the latter is stored as ordered Room rows in `proxy_app_list_selected_apps`. `AppSettingsPreferences` also stores the per-profile `trafficConfigs` JSON entries with their own mode/list fields. These are distinct persisted values; the current Android Per-App page edits the profile row.

At runtime, [`withActiveTrafficConfigApplied`](../../app/src/main/kotlin/app/TrafficConfigRuntime.kt) chooses the profile matching `activeTrafficConfigId`, falling back to the first profile if needed, and overlays that profile's Per-App mode and selected IDs onto the in-memory `AppState` used to construct VPN startup configuration. If there is no profile, it returns the existing state. `VpnApplicationPolicy` and `SkipiVpnService` then map include/whitelist, exclude/blacklist, and global modes to Android `VpnService.Builder` calls, filter user-prefixed IDs for the current Android user, and exclude SKIPI itself as required by the platform. Strict full tunnel forces global mode. This establishes active-profile precedence for Android runtime while preserving global fields for existing persistence/backup compatibility. Desktop has no equivalent runtime step.

The Android app backup format carries both contracts: global mode is in `AppBackupSettings`, global selected IDs are at `AppBackupData.proxyAppListSelectedApps`, and every profile has its own mode and selected IDs in `AppBackupTrafficConfig`. Shared mappers copy profile mode/list in both directions. Existing backup tests prove the global selected-ID fixture and generic profile mapper shape, but do not pin a non-default profile Per-App backup round-trip with unknown/legacy IDs. That is a coverage gap against the R03 backup/profile criterion, not evidence that the direct mapper currently filters those IDs.

## Data and preservation contract

Modes are numeric `0` blacklist, `1` whitelist, `2` global in the common `TrafficConfigState` and map to ordinary `[SKIPI]` strings. The document reader takes the effective last mode, trims package values, removes blank and duplicate values, and retains their order; the writer emits the mode and repeated package values in that order after the same trim/blank/dedup normalization. Legacy comment metadata is read and migrated. Clipboard import/export is already common and tested for named and legacy boolean modes, explicit user IDs, bare-name user fallback, self-package filtering when supplied, validation, Replace/Merge, mode retention, order, and deduplication.

“Unknown IDs are preserved” means configured package-ID values that have no row in the current inventory are retained when a visible row is toggled or when profile data is stored. The common selection helper appends checked row keys once and removes only the keys supplied for the unchecked row; it does not reconcile the saved list against installed apps. Existing tests include unprefixed legacy package strings and IDs for another user. It does not mean every unknown JSON key or arbitrary unknown `[SKIPI]` field round-trips.

In particular, Desktop `settings.json` and `configs.json` use typed models with `ignoreUnknownKeys`; unknown JSON object keys are ignored on read and not emitted on save. A Per-App profile edit rewrites the known `[SKIPI]` settings from `TrafficConfigState` with `withSkipiSettingsInRawConfig`, replacing that section's body while retaining other sections. Thus unknown keys inside `[SKIPI]` are not promised to survive this codec. Non-SKIPI sections remain preserved by the current profile writer. Do not expand the report or tests into a promise of arbitrary unknown-field preservation; this matches `AGENTS.md` and the accepted P04 raw-editor report.

## Existing tests and actual gaps

The accepted P04 gates already cover the portable editing path:

- Common selection tests cover shared-UID add/remove and preservation of unrelated/legacy IDs; the Android oracle has matching selection cases.
- Common clipboard tests and Android source oracles cover encode/decode/import semantics.
- Seven common controller tests cover latest-row updates, immediate mode/selection changes, Replace/Merge, missing profiles, and handled save failure. Two Desktop file-store tests reload actual temporary `configs.json` and check latest-row/library preservation.
- Eight Desktop actual-screen cases cover More → UI Edit → Per-App, mode persistence, clipboard actions, late updates, failures, Back, no-inventory behavior, and rendering. The accepted P04 full gate was 2,822 tests GREEN; two additional DNS/Resources acceptance tests were separately GREEN. Those reports explicitly did not claim Android framework/package discovery, OS clipboard, physical-device testing, or VPN enforcement.

The remaining source/test holes are narrower than the initial P04 gap:

- The projection/search/sort logic in Android `ProxyAppListData.kt` has no focused `ProxyAppListData` test class in `app/src/test`. Existing tests cover the final selection mutator, not the actual pure inventory-to-rows projection, shared-UID row model, fixed-user projection, search behavior, or refresh ordering.
- No common projection/filter/search API currently exists. `ProxyAppListSelection.kt` covers only list mutation; `ProxyAppListClipboardCodec.kt` covers serialization/import/export. Search and result state are still Android-side.
- The accepted P04 report's Desktop screen suite deliberately verifies absence of inventory and no fake rows; it does not stand in for Android package/user/icon integration.
- The backup tests include global IDs and a profile DTO mapper, but lack a targeted non-default per-profile `AppBackupTrafficConfig` round-trip assertion for mode plus legacy/unknown package IDs.
- The plan calls for Android package-list and VPN-policy smoke. Current source tests include the selection/clipboard oracles and a `StrictFullTunnelTest` that verifies strict mode forces global policy, but no focused test exercises the complete blacklist/whitelist per-profile policy mapping or a real package-provider/service interaction. Accepted P04 explicitly leaves those runtime checks open.

## Recommended narrow tests-first R03 slice

Start with the portable projection only; do not combine profile/backup, package-manager integration, and VPN service behavior into one change.

1. Add Android baseline tests beside the existing selection oracle, against the current `ProxyAppListData` implementation and plain supplied app records (no real package enumeration). Pin the actual source behavior: package-name fallback for blank labels; `userId:packageName` keys; all selection keys for same-UID rows; fixed-user remapping used in VPN-service mode; trimmed case-insensitive label/package search; and selected/shared-UID refresh ordering. Keep OS provider enumeration, icons, asynchronous refresh, and system-app filtering outside this pure baseline.
2. Port those same expected cases to common tests and record the missing common projection API as RED before production changes. Put only plain records and pure projection/filter/sort operations in a shared module with no `Context`, `PackageManager`, Android user type, Compose UI type, or `VpnService` reference. Android adapters should map actual package/user records into and out of the common values and continue supplying actual labels/icons; no provider implementation moves to Desktop.
3. Wire the Android page's existing search and row projection to the common result, keeping Android-owned query debounce, inventory refresh, user-space provider, icon fetch, and VPN-service behavior as adapters. Keep the already accepted shared mode/clipboard/controller and Desktop profile screen unchanged for this slice.
4. After that independent slice, add focused profile-document and backup round-trip tests with both profile/global stores represented. Assert that unknown/legacy package-ID values remain opaque data across profile edits and backup; assert normal trim/dedup behavior. Also explicitly pin that unknown JSON keys and unmodeled `[SKIPI]` fields are not an accepted preservation promise.
5. Finish R03 with a separate Android host gate for actual package/user adapters and per-profile blacklist/whitelist/global mapping through the Android service boundary, plus the planned Android policy smoke. Keep the existing Desktop proof focused on persistence/editor behavior and record runtime enforcement as unavailable on the current Desktop path.

This sequence continues from the current source without repeating P04's accepted shared editor/controller work or treating the absence of a Desktop package catalog as a reason to block portable editing.
