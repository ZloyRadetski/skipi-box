## Current contract and call graph

The common URI parser in [`SubscriptionInstallUri.kt`](../../shared/core/src/commonMain/kotlin/features/subscription/SubscriptionInstallUri.kt#L34) accepts direct HTTP(S) URLs or `v2rayng`, `clash`, `clashmeta`, and `flclashx` links with `install-config` or `install-sub` hosts. It rejects internal whitespace and invalid schemes/hosts/embedded URLs. Display-name precedence is query `name`, client-link fragment, URL fragment, then source default. Android’s adapter applies HTTPS-only policy and source User-Agents ([`SubscriptionInstallConfigUseCase.kt`](../../app/src/main/kotlin/features/subscription/SubscriptionInstallConfigUseCase.kt#L76)); Desktop accepts HTTP or HTTPS and supplies Desktop source User-Agents ([`DesktopSubscriptionInstallUri.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopSubscriptionInstallUri.kt#L35)).

`SubscriptionInstallOperations.prepare` is shared and pure: it reuses the first record whose URL string matches exactly, returns that complete record and catalog unchanged, and exposes its saved title; otherwise it allocates the next ID, appends an enabled row with Android install defaults, and advances the counter ([`SubscriptionInstallOperations.kt`](../../shared/app/src/commonMain/kotlin/app/skipi/app/subscription/SubscriptionInstallOperations.kt#L17)). Different fragments remain different URL strings and therefore different duplicate keys.

Android external intents are registered for the documented third-party command forms and `skipi://` in [`AndroidManifest.xml`](../../app/src/main/AndroidManifest.xml#L46). `MainActivity` handles the initial intent and `onNewIntent` ([`MainActivity.kt`](../../app/src/main/kotlin/app/MainActivity.kt#L191)); it routes `skipi://add|import/...` through the common `SkipiDeepLink` parser and routes recognized client install schemes through the HTTPS-only install parser ([`MainActivity.kt`](../../app/src/main/kotlin/app/MainActivity.kt#L293), [`SkipiDeepLink.kt`](../../shared/core/src/commonMain/kotlin/features/config/SkipiDeepLink.kt#L32)). The SKIPI subscription route supplies the localized imported name and Android’s default UA directly. That route accepts an HTTP URL because `SkipiDeepLink` classifies either `http://` or `https://` as a subscription URL; the separate third-party install URI parser remains HTTPS-only.

Android in-app text import reaches the same use case from onboarding and the proxy-list clipboard action ([`OnboardingPage.kt`](../../app/src/main/kotlin/features/onboarding/OnboardingPage.kt#L109), [`ProxyServerListActions.kt`](../../app/src/main/kotlin/features/proxy/server/list/ProxyServerListActions.kt#L173)). The use case writes the prepared catalog first, then refreshes exactly `listOf(preparedGroup.group)`, then commits a successful response ([`SubscriptionInstallConfigUseCase.kt`](../../app/src/main/kotlin/features/subscription/SubscriptionInstallConfigUseCase.kt#L36), [catalog write](../../app/src/main/kotlin/features/subscription/SubscriptionInstallConfigUseCase.kt#L115)). A failed fetch therefore leaves a newly created row persisted. Exact-URL duplicates retain all saved options, including `enabled = false`, and still go through this single-row refresh path.

Desktop currently has two UI entry points: the Add dialog and clipboard import. Clipboard text is parsed, persisted via the shared preparation and actual `DesktopSubscriptionRepository`, then refreshed by returned ID ([`DesktopProxyHome.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopProxyHome.kt#L461), [`DesktopSubscriptionInstallOperations.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopSubscriptionInstallOperations.kt#L21), [`DesktopApplicationRepositories.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopApplicationRepositories.kt#L214)). The Add dialog callback has the same prepare-then-update order ([`DesktopProxyHome.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopProxyHome.kt#L734)); Main re-reads the saved row by ID and calls shared `refreshSubscription` ([`Main.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/Main.kt#L1623)). There is no `enabled` check in this single-row path, so a disabled exact-URL duplicate is refreshed, matching Android’s single install behavior. The separate shared batch filter requires `enabled && url.isNotBlank()` ([`SubscriptionRefreshBatch.kt`](../../shared/app/src/commonMain/kotlin/app/skipi/app/subscription/SubscriptionRefreshBatch.kt#L17)); disabled and blank-URL rows are excluded from bulk refresh.

The installed record’s saved UA, Age key, and `updateViaProxy` drive refresh. Android reads current AppState options when the request starts: per-row proxy/Age settings plus process-wide device-header and timeout settings ([`SubscriptionUpdateUseCase.kt`](../../app/src/main/kotlin/features/subscription/usecase/SubscriptionUpdateUseCase.kt#L270)); defaults are headers enabled and 10 seconds ([`AppState.kt`](../../app/src/main/kotlin/app/AppState.kt#L138)). Desktop takes current Desktop settings and active Core listener facts when preparing fetch options, including timeout, proxy, device headers, Age key, and blank-UA fallback ([`DesktopLocalProxyRuntime.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopLocalProxyRuntime.kt#L47), [`Main.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/Main.kt#L1639)). The default Desktop timeout is 30 seconds, versus Android’s 10; Desktop’s blank raw-install UA stays empty in storage and fetch falls back to the Desktop setting/default. Recognized client links store their source UA. Both paths use shared Age policy and the stored per-row key ([`SubscriptionAgePolicy.kt`](../../shared/core/src/commonMain/kotlin/features/subscription/SubscriptionAgePolicy.kt#L13), [`DesktopSubscriptionFetcher.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopSubscriptionFetcher.kt#L50)). These are current host differences; this audit does not infer a required change to established Desktop defaults.

An embedded profile returned by the subscription fetch stays in the shared refresh handoff. Stale/deleted subscription identity withholds the profile alongside other refresh writes ([`SubscriptionRefreshOperation.kt`](../../shared/app/src/commonMain/kotlin/app/skipi/app/subscription/SubscriptionRefreshOperation.kt#L142)). Android applies it to latest AppState; Desktop reads the latest config library at commit and preserves the source `activate`/existing-profile policy ([`DesktopSubscriptionRefreshCommitAdapter.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopSubscriptionRefreshCommitAdapter.kt#L133)). Current source contains no separate install-specific pending-profile queue.

## Findings

### Current behavior gaps or route limits

- **Desktop external/CLI launch is absent from the current Kotlin entry point.** `main()` takes no arguments ([`Main.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/Main.kt#L115)); no Desktop code calls `parseSkipiDeepLinkOrNull`, and `DesktopSubscriptionInstallUri` is reached through UI input/clipboard only. I found no Desktop URI registration in the inspected workspace sources. The current S03 plan says to connect Desktop but does not explicitly require OS protocol registration; this is an actual gap only if the intended S03 route includes externally launched or CLI-provided URIs. Packaging-level registration was not tested.
- **Desktop Add-field validation blocks the custom client schemes its callback can parse.** `SkipiAddSourceDialog` enables subscription submit only for `isValidManualSubscriptionUrl()`—HTTP(S) ([`SkipiAddSourceDialog.kt`](../../shared/ui/src/commonMain/kotlin/app/skipi/ui/home/dialogs/SkipiAddSourceDialog.kt#L81), [submit gate](../../shared/ui/src/commonMain/kotlin/app/skipi/ui/home/dialogs/SkipiAddSourceDialog.kt#L260)). Thus `v2rayng://…`/`clash://…` cannot reach `DesktopProxyHome.onSaveSubscription`; those schemes work through the separate clipboard-import route.
- **Desktop duplicate messaging loses Android’s saved-title notice.** The shared preparation exposes `existingTitle`, and Android uses it for an “already exists” message ([`SubscriptionInstallConfigUseCase.kt`](../../app/src/main/kotlin/features/subscription/SubscriptionInstallConfigUseCase.kt#L58)). Desktop reduces preparation to an ID; clipboard success then says the incoming parsed name was added ([`DesktopSubscriptionInstallOperations.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopSubscriptionInstallOperations.kt#L22), [`DesktopProxyHome.kt`](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopProxyHome.kt#L466)). The record itself is correctly reused unchanged; this is a user-visible duplicate notice difference, not a persistence or refresh mismatch.

### Verification gaps (source evidence is present, route behavior is not exercised)

- No current test drives `MainActivity`/the Android manifest intent filters, `onNewIntent`, onboarding text caller, or proxy-list clipboard caller end to end. Android parser and use-case unit tests do not verify OS dispatch or UI notices.
- No current test drives Desktop `DesktopProxyHome` or the `Main` install callbacks together. Repository tests verify persistence, but not that a user route observes the persisted row before the actual fetch callback, nor that the callback refreshes a disabled duplicate. There is no Desktop CLI/OS launch test.
- Install-specific tests do not assert the UA/device headers/Age header/timeout/proxy values sent on the first request. Source mappings are present and broader refresh/fetcher tests cover shared request/decryption and options behavior, but not the install-to-request composition.
- Refresh/profile tests cover the common embedded-config handoff and Desktop latest-library/activation commit, but an install-specific successful response carrying an embedded profile is not covered.
- Current documented Android third-party commands align with the manifest (`v2rayng://install-sub`; the other three use `install-config`) ([`SkipiUrlSchemesScreen.kt`](../../shared/ui/src/commonMain/kotlin/app/skipi/ui/settings/SkipiUrlSchemesScreen.kt#L234)). Common parser tests accept additional source/host combinations; no requirement was found that every combination be externally registered.
