# S03 install integration proposal

Status: root-approved integration proposal with new tests drafted on separate files. This child did not run Gradle or Git; the root owns those operations.

## Scope

Keep this slice to existing subscription-install paths and one single-subscription refresh. Android keeps its current HTTPS-only manual/third-party install parsing and its existing `skipi://add|import` Activity route. Desktop manual Add remains HTTP(S)-only, matching the Android manual field. Do not add a custom-scheme Add dialog, Desktop OS protocol registration, or a CLI argument receiver in this slice.

S03 says to reuse one-subscription refresh for “install URI/deep-link” and requires the common scenario to be wired to Android UI/background and Desktop ([plan.md:295-301](../../tasks/plan.md#L295)). Android already handles its external SKIPI subscription deep link through the common `SkipiDeepLink` parser and the install use case ([MainActivity.kt:293-352](../../app/src/main/kotlin/app/MainActivity.kt#L293), [SkipiDeepLink.kt:32-42](../../shared/core/src/commonMain/kotlin/features/config/SkipiDeepLink.kt#L32)). Desktop currently accepts direct/client install URIs in its existing clipboard and Add-dialog flows; neither route calls the shared SKIPI deep-link parser ([DesktopSubscriptionInstallUri.kt:35-52](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopSubscriptionInstallUri.kt#L35), [DesktopProxyHome.kt:461-474](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopProxyHome.kt#L461)). Root has resolved the bounded interpretation for this slice: the existing Desktop clipboard handler may recognize shared `SkipiDeepLink.Subscription` (`skipi://add|import/...`) and pass its decoded URL into the install operation. Keep this recognition clipboard-only; the manual Add dialog remains HTTP(S)/existing client install URI only. External Desktop launch/CLI remains a later boundary.

## Source-backed behavior to preserve

- `SubscriptionInstallOperations.prepare` is already the shared exact-URL decision: duplicates reuse the complete saved record and expose its saved title; new records use Android-compatible defaults ([SubscriptionInstallOperations.kt:10-57](../../shared/app/src/commonMain/kotlin/app/skipi/app/subscription/SubscriptionInstallOperations.kt#L10)). Keep the incoming parsed User-Agent only for newly created rows. A duplicate keeps its stored name, User-Agent, Age key, enabled state, proxy flag, metadata, and other fields.
- Android already persists before calling its single-row refresh, includes disabled exact-URL duplicates in that call, and reports the saved duplicate title ([SubscriptionInstallConfigUseCase.kt:32-55](../../app/src/main/kotlin/features/subscription/SubscriptionInstallConfigUseCase.kt#L32)). Preserve `applyProxySubscriptionUpdates` as the success commit path so embedded subscription profile content still reaches the existing traffic-config integration.
- Desktop currently persists in `prepareAndPersistIn`, then its two UI callers separately invoke `onUpdateSubscriptionById`; that callback re-reads the saved row, builds current fetch options, and runs shared `refreshSubscription` with the Desktop commit adapter ([DesktopSubscriptionInstallOperations.kt:21-32](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopSubscriptionInstallOperations.kt#L21), [DesktopProxyHome.kt:461-472](../../desktopApp/src/main/kotlin/app/skipi/desktop/DesktopProxyHome.kt#L461), [Main.kt:1623-1685](../../desktopApp/src/main/kotlin/app/skipi/desktop/Main.kt#L1623)). The single path has no enabled check, so a disabled duplicate is refreshed as on Android. Keep batch eligibility (`enabled && nonblank URL`) separate from install eligibility.
- First-fetch parameters remain host-derived at request time. Android derives `updateViaProxy && proxyRunning`, the saved Age key, global device-header setting, and configured timeout from current state; Desktop derives the saved proxy/Age values and current Desktop settings/Core state. Keep source-specific UA parsing and the Android HTTPS / Desktop HTTP(S) policies intact.
- Preserve pending/embedded-profile handling in the existing refresh commit adapters. The common loader carries a `ResolvedEmbeddedSubscriptionConfig`; Android applies it through `applyProxySubscriptionUpdates` / `commitSubscriptionRefresh`, and Desktop uses its refresh commit adapter. Install orchestration must call these existing refresh paths rather than creating a second direct-fetch/commit route.

## Minimal seam

Keep `prepare(...)` pure, and add one narrow common orchestration operation in `shared/app` that accepts the current `SubscriptionRepository`, parsed `title/url/userAgent`, and a host-supplied suspend callback for the real single refresh. Its conceptual contract is:

```kotlin
suspend fun <RefreshResult> installAndRefresh(
    repository: SubscriptionRepository,
    title: String,
    url: String,
    userAgent: String,
    refresh: suspend (SubscriptionRecord) -> RefreshResult,
): SubscriptionInstallAndRefreshResult<RefreshResult>
```

The operation calls `repository.updateCatalog` with `prepare(latestCatalog, ...)`, captures that preparation, waits for the repository write to finish, then invokes `refresh(preparation.subscription)` exactly once and returns both the preparation (including `existingTitle`) and the host refresh result. The callback owns only host transport/options/commit behavior; it must receive the saved full record and remain the existing shared single-refresh route. Do not use `SubscriptionRepository.refresh(id)` as the install refresh port: the Desktop repository's default callback reports unsupported, while its current functional refresh is wired through the richer host operation.

Android's `SubscriptionInstallConfigUseCase.install` should continue resolving the just-persisted `SubscriptionGroupState` and call the existing `updateSubscriptions` + `applyProxySubscriptionUpdates` path from the callback. Desktop should extract the current fetch/parse/commit body from the `onUpdateSubscriptionById` UI callback into one app-lifetime suspend single-refresh operation that accepts the current saved `SubscriptionRecord` and returns enough structured result/failure information for the scheduler to preserve transient/permanent classification. The manual refresh UI callback can remain a presentation wrapper around that operation; install invokes it after persistence through `installAndRefresh`, and periodic scheduling invokes it with the current saved record (looked up from its group ID). This keeps fetch options, effective Desktop fallback User-Agent, commit/profile handoff, and refresh result semantics in one place. The install UI also needs the returned saved title for duplicate wording and should wait for the refresh result before showing the final message, so failure is not reported as an unconditional “added” success.

Add a small host-neutral UI formatter, `formatSubscriptionInstallMessage(existingTitle, refreshMessage, existingUrlTemplate)`, that returns the refresh message for a new row and prepends the saved-title duplicate notice for an exact URL match. Android's current `subscriptionInstallMessage` can delegate to it after it formats its existing update result; Desktop can combine its real single-refresh summary with the same helper without depending on Android update types.

## New behavioral tests before production changes

1. **Common install orchestration test:** use a fake `SubscriptionRepository` that exposes the updated catalog before returning from `updateCatalog`. Assert the refresh callback is called once and sees the persisted row. Cover a new row and an exact-URL duplicate with a deliberately disabled, configured record. For the duplicate, assert catalog equality, full-record equality, saved `existingTitle`, and no overwrite from incoming title/UA. For a new row, assert the existing Android defaults and that a refresh failure/exception leaves the row persisted.
2. **Android first-fetch and profile handoff test:** use the existing real local HTTP fetcher and capture actual request headers. Cover a disabled exact-URL duplicate's saved User-Agent and Age key, plus a new row's Android defaults, device header, timeout, and non-activating embedded profile import. The existing install failure-persistence test remains in place.
3. **Desktop coordinator integration test:** exercise `installAndRefresh` against the real Desktop repository adapter. Assert persistence precedes one refresh, disabled duplicate fields remain intact, and the returned preparation retains the saved title. The app-level single-refresh extraction and periodic invocation remain production integration work for the root/scheduler agent.
4. **Desktop clipboard parser test:** assert percent-decoded shared `SkipiDeepLink.Subscription` links are accepted only by the existing clipboard parser, direct/client URI parsing still works, malformed and non-subscription SKIPI links fall back, and the manual Add parser still rejects a SKIPI custom link. Do not add an external Desktop protocol/CLI test in S03.
5. **Shared message formatter test:** new installs return the refresh message unchanged; exact duplicates prepend the formatted saved-title notice while retaining the refresh success/failure detail.

These new test files are `shared/app/src/commonTest/kotlin/app/skipi/app/subscription/SubscriptionInstallAndRefreshTest.kt`, `shared/ui/src/commonTest/kotlin/app/skipi/ui/home/SubscriptionInstallMessageTest.kt`, `app/src/test/kotlin/features/subscription/SubscriptionInstallFirstFetchTest.kt`, `desktopApp/src/test/kotlin/app/skipi/desktop/DesktopSubscriptionInstallIntegrationTest.kt`, and `desktopApp/src/test/kotlin/app/skipi/desktop/DesktopSubscriptionClipboardInstallTest.kt`.

Existing tests already cover pure duplicate/default preparation, Android persistence before a failed fetch and saved duplicate title, parser policies, and Desktop persistence/duplicate preparation. The missing evidence is orchestration ownership/one-call behavior, captured Android first-fetch options, profile handoff through install, and Desktop saved-title plus single-operation behavior. No baseline Android Git-history comparison was performed because root owns Git operations.

## Gaps classified

**Actual behavior gap:** Desktop's current install orchestration is split across UI callbacks and discards `existingTitle` before the duplicate notice; clipboard reports the incoming name as “added.” The single refresh currently executes after persistence, but current source/tests do not establish that one install operation owns this sequence. Desktop external/CLI launch is absent and is explicitly outside this slice unless scope is reopened.

**Verification gaps:** the new tests capture real Android first-fetch request behavior and exercise the shared persist-then-refresh coordinator, but require the production APIs to exist before verification can pass. Desktop app-lifetime single-refresh extraction, caller messaging, and scheduler invocation still need production integration and host-level verification. The approved clipboard coverage is deliberately confined to the existing clipboard route; it does not establish Desktop OS registration or external CLI behavior.
