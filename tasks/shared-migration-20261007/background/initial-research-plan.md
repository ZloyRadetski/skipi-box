# План ресёрча переноса Android-кода в shared

Актуальный сводный порядок работ на 6 октября 2026 года: [подробный план](/home/vqsego/TorvaldsVPN/Skipi/skipi-box/tasks/shared-migration-roadmap.md) и [чек-лист](/home/vqsego/TorvaldsVPN/Skipi/skipi-box/tasks/shared-migration-todo.md). Ниже сохранены исходный план исследования и выводы аудита, включая историческое состояние до уже выполненных изменений.

## Цель

Составить проверенную по исходникам карту миграции: что уже общее, что пока реализовано только в Android/Desktop и может стать общим, а что должно остаться платформенным адаптером. На основе карты предложить порядок дальнейшего переноса. На этом этапе код не менять и проверки не запускать.

## Зафиксированный scope

- Целевые платформы: Android и Desktop JVM. iOS не планируется.
- Desktop не обязан повторять полный набор Android-функций. Общие переносимые модели, политики, операции и UI используются там, где это сокращает дублирование или стоимость поддержки; Desktop-экраны и OS-интеграции добавляются только для нужных Desktop-сценариев.

## Порядок исследования

1. Уточнить текущие платформенные цели и границу между общим кодом и нативными движками/сервисами.
2. Разобрать `shared:core`: модели, политики, парсинг, чистые use cases и оставшиеся platform source sets.
3. Разобрать `shared:app`: state/store, контракты репозиториев, Android/Desktop реализации и переходные мосты.
4. Сопоставить `shared:ui` с Android и Desktop по сценариям: Home, настройки, конфигурации, серверы, подписки, маршрутизация, диагностика и onboarding.
5. Проследить Android/Desktop composition roots, persistence, runtime, OS APIs и оставшиеся экраны/потоки.
6. Свести результаты в матрицу статусов, определить архитектурные риски/зависимости и предложить безопасные вертикальные срезы для продолжения.

## Критерии завершения

- Для каждой области указано, что именно уже вынесено и где это подключается.
- Оставшиеся Android-only части разделены на переносимую логику/UI и необходимые OS-адаптеры.
- Неоднозначности отмечены как вопросы, без предположений о целевом наборе платформ.
- Рекомендации упорядочены по зависимостям и размеру вертикального среза.
- Рабочий код не изменён; никаких тестов или сборок не запускалось.

## Аудит до изменения store (состояние на 2026-10-03)

Выводы ниже фиксируют архитектуру до первого вертикального среза. Состояние после среза и его проверки описаны в [verification.md](store-consolidation-20261003/verification.md).

- Текущие shared-цели — Android и Desktop JVM; iOS-цель не настроена. Go SKIPI Core остаётся отдельной нативной зависимостью.
- `shared:core` уже покрывает много переносимых моделей и политик. `shared:app` содержит общие контракты и store, но Android продолжает сохранять legacy `AppState`; общий store строит состояние из репозиториев и не является самостоятельным хранилищем.
- Android composition создаёт два `SharedApplicationStore` с разным runtime wiring. Часть вызовов идёт через `AppServices`, часть через `AndroidAppStateStore`; сначала нужно свести их к одному явно настроенному пути.
- Home — уже общий вертикальный срез для Android и Desktop. Расширять его перенос без конкретного остатка не приоритетно.
- В `shared:ui` есть общие настройки, конфигурации, routing, onboarding и diagnostics UI, но их наличие не означает одинаковое использование: Desktop сейчас сохраняет собственные экраны конфигурации и настроек.
- Переносимые правила Network Automation уже в `shared:core`, но её настройки и правила ещё не входят в shared persisted settings/контракты; Android-монитор сети, разрешение SSID и команды туннелю остаются платформенными.
- В Desktop application factory не подключены optional routing/resource репозитории. Общий контракт proxy catalog обещает атомарное обновление, но Android переопределяет операцию атомарно, а Desktop использует пошаговую реализацию по умолчанию.

## Рекомендуемый порядок реализации после ресёрча

1. [x] Свести Android к одному `SharedApplicationStore` с process runtime-state repository, читающим фактический статус VPN-сервиса и кеш traffic sampler, и выбрать единый action path для мигрированных функций. Выполнено в первом шаге; см. [проверку консолидации](store-consolidation-20261003/verification.md).
2. Уточнить host capabilities и гарантии контрактов для сценариев, которые действительно используют оба хоста, в первую очередь атомарность proxy catalog. Не подключать Desktop routing/resources только ради формального паритета; сохранить Room/SharedPreferences и Desktop JSON как адаптеры существующего хранения.
3. Переводить оставшихся Android-потребителей на общие репозитории по уже существующим общим сценариям: proxy catalog, subscriptions, traffic configs и routing. Для каждого среза убирать прямую запись старого `AppState` только после подключения соответствующего репозитория.
4. Для Network Automation оставить Desktop-поддержку вне scope. Модель и чистая политика уже могут оставаться общими; перенос Android-настроек в общий UI/state оправдан только если это упрощает Android-архитектуру без добавления лишнего host-capability слоя. Получение network facts, разрешение SSID и запуск VPN остаются Android adapter.
5. Отдельно оценить остаток Xray config composition: переносить только чистое построение планов/данных, не runtime и нативный запуск.
6. Сохранять разные Desktop и Android flows там, где различаются продуктовые сценарии. Например, Desktop raw `.conf` library и Android visual traffic profiles не объединять только из-за общего слова «конфигурации».
