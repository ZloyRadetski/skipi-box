**Состояние на 2026-10-06.** Цель — переносить общие для Android и Desktop JVM правила, модели, операции и интерфейсные компоненты, когда это упрощает сопровождение совпадающих продуктовых сценариев. Ближайший согласованный срез — общие правила выдачи ID при импорте и добавлении серверов. Последующие направления упорядочены по зависимостям, но перед реализацией каждое нужно уточнить по реальным потребителям.

## Общий рабочий порядок

Для каждого среза сначала пройти фактический путь данных: точка входа Android/Desktop, общие функции и репозитории, адаптер хранения, системные эффекты, тестовые швы. Не считать наличие общего Compose UI или API доказательством, что потребитель уже подключён. Зафиксировать сохранённое поведение и продуктовые решения; уточнять у пользователя только вопрос, ответ на который действительно меняет продукт и не выводится из текущего контракта.

Исследование, разработку содержательных тестов и изменения кода делегировать исполнителям GPT-6 Luna max. Корневой агент координирует работу, независимо проверяет реализацию, запускает верификацию и коммитит только исходники и тесты. Пользователь уже одобрил этот порядок, поэтому подтверждения на каждом промежуточном шаге не нужны. Если меняется поведение, тест должен показать соответствующий поведенческий RED до реализации; при чистом рефакторинге допустимы проходящие тесты сохранения поведения. Ошибка компиляции не является поведенческим RED. После реализации нужны сфокусированные успешные проверки, подходящие наборы Android/Desktop JVM-тестов, независимое ревью и целевая сборка, когда она проверяет затронутую границу.

Планы и чек-листы остаются вне Git index и коммитов. Сохранять существующую работу в подмодуле нативного движка и пользовательские данные. Room, SharedPreferences и Desktop JSON остаются адаптерами; полной замены хранения не требуется. Атомарное обновление каталога не образует транзакцию между каталогом и подписками. Успешный возврат Android-операции сам по себе не подтверждает долговечную запись Room.

Сначала выполнять только сфокусированные тесты затронутого слоя; полную интеграцию запускать после стабилизации кода и ревью, а не после каждого изменения планов. Из корня `/home/vqsego/TorvaldsVPN/Skipi/skipi-box` выполнить такую Android/Desktop команду:

При отчёте отдельно указать результаты наборов Android и Desktop тестов, сборки и ручные проверки интерфейса/устройства, если они выполнялись; не выдавать сборку APK за проверку пересборки нативного движка или реального устройства.

## Ближайший срез: выделение ID при импорте и добавлении

Общие парсеры и их упорядоченная цепочка уже существуют. Ручные действия изменения и выбора сервера уже используют общие actions в соответствующих путях; задача — найти подтверждённые пробелы в распределении ID, обновлении каталога и подключении потребителей, а не переносить парсеры заново.

**Исследование.** Сопоставить реальные пути Android и Desktop: URL, текст/буфер обмена, файл, ручной ввод и создание при первичной настройке; отдельно отметить Android-only источники вроде QR, если они приходят к тем же правилам. Проследить общий `importProxyServerPayload`, действия каталога, репозитории хостов и создание серверов при сверке подписок. Установить, какие точки входа уже вызывают общие операции, а какие всё ещё обходят их. Два проверяемых места общей функции преобразования каталога: `importProxyServerRecords` повышает счётчик через `id++`, а `saveProxyServerRecord` вычисляет `serverId + 1`; оба выражения нужно проверить на исчерпании диапазона `Int`.

**Требования и тесты.** До изменений зафиксировать порядок импортируемых и существующих записей, выбранный сервер, группы, сведения об источнике и текущую политику частичного импорта/дедупликации. Если продукт принимает допустимую часть частично распознанных данных, это поведение нужно сохранить. Это не то же самое, что провал применения уже собранного каталога: отказ из-за валидации, нехватки ID или ошибки сохранения Desktop не должен частично публиковать новое состояние каталога. Добавить тесты на свободный диапазон, ID около `Int.MAX_VALUE`, пакет больше числа оставшихся ID, сохранённый верхний счётчик next ID, записи неизвестного формата и сбой сохранения. Не вводить новую политику «всё или ничего» для частичного разбора без отдельного решения.

**Реализация и проверка.** Исправить или обобщить выделение ID в общем слое, затем подключить только подтверждённые обходящие потребители к существующему действию обновления каталога. Новые ID должны быть уникальными и монотонными; при исчерпании пакет отклоняется целиком без переполнения и частичной публикации. Существующие ID и порядок сохраняются; удаление не уменьшает счётчик. Проверить тесты функции преобразования каталога и `SharedApplicationStore`, тесты отображения Android-данных и действий, а также тесты Desktop-репозитория и импорта; затем соответствующие наборы Android/Desktop JVM-тестов и сборки APK/Desktop. Если изменился видимый путь импорта, вручную проверить его на доступной платформе. Ошибка сохранения Android, которая лишь запускает асинхронную запись, не должна описываться как проверенная долговечность Room.

Основные точки кода: [общие операции каталога и выдача ID](/home/vqsego/TorvaldsVPN/Skipi/skipi-box/shared/app/src/commonMain/kotlin/app/skipi/app/proxy/ProxyServerCollectionOperations.kt), [общая точка входа импорта](/home/vqsego/TorvaldsVPN/Skipi/skipi-box/shared/app/src/commonMain/kotlin/app/skipi/app/proxy/ProxyServerImportOperations.kt), [общий store](/home/vqsego/TorvaldsVPN/Skipi/skipi-box/shared/app/src/commonMain/kotlin/app/skipi/app/store/SharedApplicationStore.kt), [Android use cases для proxy](/home/vqsego/TorvaldsVPN/Skipi/skipi-box/app/src/main/kotlin/features/proxy/server/usecase/ProxyServerUseCases.kt), [Desktop фиксация импорта](/home/vqsego/TorvaldsVPN/Skipi/skipi-box/desktopApp/src/main/kotlin/app/skipi/desktop/DesktopProxyImportCommitter.kt).

## Сразу после импорта: аудит Android операций удаления и запуска

Этот аудит нужен до расширения похожих операций каталога. Известно, что Android-блокировка защищает ветку удаления, где сначала требуется остановить туннель; прямое удаление может пересечься с запуском или перезапуском. Сначала описать конкурирующие состояния и протестировать реальный координатор. Приёмка: тесты показывают корректное разрешение гонки для прямого удаления, остановки/удаления и запуска/перезапуска; поведение статуса сервиса после остановки/удаления остаётся сохранённым; синхронизация ограничена реально конкурирующими действиями. Проверка — Android-тесты координации операций до/после, затем набор JVM-тестов приложения. Если изменился видимый сценарий, вручную проверить удаление при переходах состояния. Не считать текущую синхронизацию после stop решением прямой ветки и не проектировать заранее глобальную блокировку или транзакцию каталога.

## Последующие направления

Пункты ниже задают порядок исследования, а не один большой пакет реализации. Перед каждым направлением его нужно разделить на малые вертикальные срезы с отдельными критериями приёмки. Если исследование покажет, что у платформы нет такого сценария или дублирования нет, платформенно-специфичный перенос не добавлять.

1. **Оставшиеся потребители каталога.** Зависит от общей политики ID и проверки операций VPN выше. Найти прямые изменения каталога Android/Desktop, которые остались после уже завершённого удаления и других подключённых действий. Приёмка: каждый выбранный путь использует общие действия и контракты репозитория, сохраняя порядок, выбор, группы, ID и ссылки цепочек/стратегий; платформенные остановка VPN, переподключение и сообщения выполняются в нужных местах. Проверка: тесты общих правил и затронутых платформенных действий, затем интегрированные JVM-тесты. Для изменённых экранных действий — ручная проверка добавления и удаления на соответствующей платформе.

2. **Подписки и операции обновления.** Зависит от стабильного контракта каталога. Сопоставить Android-обработчики и фоновые задачи обновления, Desktop-загрузку и сохранение результата, существующие общие операции сверки и обновления подписок. Выносить согласование данных, сохраняя адаптеры HTTP, планирования, уведомлений и фоновых задач. Приёмка: общие части сохраняют группу, источник, время обновления и правила поведения при частичном сбое; обе платформы используют общее правило там, где сценарий совпадает; сетевые и фоновые механизмы вызываются через подходящие адаптеры. Проверить общую логику на тестовых данных и затронутые Android/Desktop-адаптеры. Если меняется экран обновления, проверить его вручную. Для операции, меняющей каталог и подписку, отдельно определить порядок записи и восстановления при сбое; единую транзакцию нескольких хранилищ заранее не обещать.

3. **Конфигурации трафика и библиотека конфигураций.** Зависит от завершения тех операций каталога, на которые ссылаются конфигурации; отдельные чистые операции можно переносить независимо. Исследовать сохранение, применение, импорт/экспорт и автообновление Android-потребителей. Общие модели и операции уже есть, но их подключение нужно проверить. Библиотека исходных `.conf` на Desktop и визуальные профили трафика Android сохраняют свои различия там, где пользовательские сценарии не совпадают. Приёмка: перенесённый потребитель сохраняет порядок, выбранную/активную конфигурацию, правила и обработку ошибок записи; планировщики и фоновые задачи остаются в платформенном слое. Проверить общие операции и затронутые адаптеры хранения; изменённый редактор или импорт вручную проверить на соответствующей платформе.

4. **Маршрутизация и ресурсы по потребности.** Зависит от каталога, ссылок подписок и реальных сценариев каждой платформы. Проверить Android-потребителей и сборку графа зависимостей Desktop. Приёмка: общие правила сохраняют ссылки на исходящие подключения и ресурсы; подключение Desktop-репозитория и UI оправдано нужным сценарием или упрощением общей реализации; файловые операции и действия движка остаются за адаптерами. Проверить общие операции и задействованные адаптеры. Изменённый экранный сценарий проверить вручную на соответствующей платформе.

5. **Условный перенос состояния и UI автоматизации сетей.** Чистые правила принятия решений уже находятся в `shared:core`; поддержка этой функции на Desktop не обязательна. После основных срезов исследовать, уменьшит ли перенос Android-настроек и состояния правил в общие модели дублирование. Приёмка: общий слой содержит переносимые правила и данные; получение сведений о сети, разрешения для SSID, мониторинг и VPN-команды остаются Android-адаптерами. Выполнять перенос, если он упрощает архитектуру. Проверить тесты общей политики и Android-координации/разрешений; изменённый экран настроек пройти вручную на Android.

6. **Остаток построения Xray-конфигураций.** После миграции потребителей проверить, остались ли дублированные чистые правила построения конфигурации. Приёмка: переносится детерминированное построение планов и данных с проверяемой общей границей; запуск Xray и чтение платформенных ресурсов остаются за адаптерами. Проверить построение конфигураций на тестовых данных и сборку затронутых Android/Desktop-модулей; изменённый пользовательский сценарий работы с конфигурацией проверить вручную.

7. **Итоговый аудит UI и постепенная очистка.** Зависит от подключения предыдущих сценариев. Составить карту совпадающих Android/Desktop-сценариев, затем убирать дублирование там, где совпадают требования. Приёмка: общие компоненты действительно подключены, совпадающее поведение реализовано одним кодом, необходимые платформенные различия сохранены; удаляемые обёртки `AppState` не имеют потребителей. Проверить Android/Desktop JVM-тесты и соответствующие сборки; вручную пройти изменённые пользовательские сценарии на обеих платформах. Удалять устаревшую логику по одному заменённому пути. Полная перепись состояния и хранения в этот этап не входит.

## Условия завершения миграции

Для Android и требуемых Desktop-сценариев есть проверенная карта «точка входа → общая операция → платформенный адаптер». Переносимый контракт используется там, где совпадает поведение; системные API, хранение и нативный запуск остаются за адаптерами. Все мигрированные сценарии проходят подходящие тесты, ревью и нужные сборки; ограничения проверок и нерешённые различия зафиксированы. В коммиты попадают только исходники и тесты; пользовательские данные и прежняя работа в нативном подмодуле сохранены.
