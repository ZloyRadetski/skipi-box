## Resulting structure

The shared layers own the portable resource model and decisions. `shared/core` contains resource kinds/statuses, the five-provider source catalog and profile resolver, filename and restore policies, ordered download plans, HTTP transfer behavior, cancellation/proxy policies, write serialization, batch progress/execution, and periodic/one-time refresh state. `shared/app` contains editor operations, file-operation and update-queue contracts, and the synchronized update coordinator. `shared/ui` contains the resource-management screen, cards, dialogs, and presentation helpers used by Android and Desktop.

Hosts retain the operations that depend on their runtime. Android supplies scoped storage paths, SAF/`Uri` access, real `Os.rename`, its authenticated proxy/VPN connection behavior, notifications, permissions, and WorkManager. Desktop supplies profile-local files, strict same-directory atomic publication, the Swing picker, `HttpURLConnection`/SOCKS bindings, and an app-lifetime refresh host with in-app feedback only; it has no system notifications or OS-level background work. Desktop profiles with no explicit resource User-Agent use the established `Skipi/<version>/Desktop` fallback; an explicit profile value, including blank, continues to take precedence. The legacy global `ResourceRepository`/`AppState` mirror remains for compatibility and is not consumed by the production resource page. The resource page uses settings for its `trafficConfigId` (which can identify an inactive profile), and manual requests capture that profile; the automatic worker reloads the profile named by its request ID before checking eligibility and updating it.

The shared UI keeps the Android screen's five built-in rows in their original order, then lists profile custom files. It does not expose the Xray Core file as a downloadable geo row. Source editing still saves the five custom URLs and then commits custom-source selection as a separate settings update. CRUD metadata is committed before its corresponding file operation. Android's page is now a thin host adapter over that screen.

## Refresh source facts and verified boundary

The refresh policy was compared with the Android gateway and `ResourceAutoUpdateWorker`, including WorkManager 2.11.2 source and cached bytecode. `WorkRequest.DEFAULT_BACKOFF_DELAY_MILLIS` is 30 seconds and `MAX_BACKOFF_MILLIS` is five hours. Android periodic geo work requires a connected network, sets a 15-minute exponential-backoff base, and is capped at five hours. Android one-time geo work uses unique-work `REPLACE`, does not set a custom backoff, and therefore uses the 30-second default base. WorkManager calculates a retry time as `lastEnqueueTime + base × 2^(attempt − 1)`, capped at five hours; `WorkerWrapper.reschedule()` updates `lastEnqueueTime` to the current time, and `resetPeriodic()` updates it on success while resetting attempts and advancing the period count. The one-time and periodic retry paths therefore keep distinct bases. The worker reloads the latest profile by ID and checks `resourceSettings.autoUpdate` before repository work; it does not re-check the source, interval, or provider fields. The common tests pin the portable policy and formula, not WorkManager execution itself.

Android's active-profile observer drops its initial observation; a later change to the current profile ID or custom GeoIP/GeoSite URL can queue one-time `REPLACE` work for a positive profile ID. Shared trigger state uses that same triple. Manual queue cancellation disconnects the tracked active HTTP connection. Scheduled worker cancellation is a different path: it cancels coroutine work cooperatively, and existing synchronous Android network I/O can finish its in-flight transfer before the worker stops. The focused Desktop integration tests exercise same-profile one-time replacement, independent one-time/periodic jobs, periodic removal/disable cancellation, re-enabling, and app-scope cancellation. Desktop's updater is an in-process host, not a system scheduler: it can run only while the application process is active and provides no system notifications or OS-level background execution. Its network check treats an up, non-loopback interface as connected; that is an OS-interface approximation and does not establish external reachability.

The focused `DesktopResourceAutoUpdater` tests also pin the generation guard that prevents an older same-profile one-time attempt from deleting its replacement, and that a changed active source cancels only the profile's one-time job. Removing periodic eligibility cancels its running updater job without cancelling a distinct running one-time request. Scheduled job cancellation remains cooperative at the coroutine boundary; it does not mean the same thing as manual queue cancellation's active-connection disconnect.
